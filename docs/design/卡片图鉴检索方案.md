# 卡片图鉴检索方案

状态：第一期与第二期已于2026-10-12实施（v0.3.0 工作区，尚未发版）；实施差异见第9节。原提案基于 v0.3.0 代码盘点。范围仅限「数码图鉴 → 卡片」页签；数码兽页签、伙伴图鉴、道具图鉴保持不变。文中数量均以当前107张非故障牌的基础版统计，实施时由代码实时计算，不写死。

## 1. 现状与问题

当前实现位于 `src/components/Codex.tsx`，卡片页提供5个下拉框：搭档（四位搭档／通用）、类型、费用（0／1／2）、收录（全部／已收录／未收录）、排序（费用／成长阶段／名称）。

| 问题 | 具体表现 |
| --- | --- |
| 没有关键词搜索 | 想找「灼烧」「抽牌」「护盾」相关的牌，只能在107张卡中逐张翻看 |
| 筛选粒度太粗 | 只能按搭档筛，不能按形态（如只看红莲骑士兽的4张）或成长阶段筛；阶段只能用来排序 |
| 下拉框只能单选 | 「1费或0费」「攻击或强化」这类组合无法表达；每次切换都要重新打开下拉框 |
| 没有机制分类 | 灼烧、符印、蓄能、噬能、自损、群体、多段等核心玩法只存在于卡面文字，无法检索；也无法区分「施加灼烧」和「利用灼烧」 |
| 强化信息不可见 | 只展示基础版；15张牌强化后费用会变（14张变为0费，数据修复2→1费），按费用筛选时这些牌查不到 |
| 结果反馈弱 | 只有「共N张」；看不出当前生效了哪些条件，没有一键清除，结果为空时也没有提示 |
| 状态不保留 | 关闭图鉴后所有筛选重置 |
| 没有详情 | 点击卡片没有反应；看不到强化对比、所属形态和获取方式 |

另外有一个数据口径问题：小妖兽各分支的专属牌 `family` 都是 `impmon`，其他搭档的究极体牌则用分支ID（`duke`、`sakuya` 等）。现有 `groupOf()` 会向上回溯到搭档，所以目前没出错；但如果要按形态筛选，必须改用 `unlockForm`／`unlockForms`，不能用 `family`。

## 2. 目标与不做

目标：玩家能用三种方式快速找到卡，并且可以组合使用。

1. 关键词：输入卡名、效果片段、形态名或机制词，立即出结果。
2. 分类：按来源（搭档→形态）、阶段、类型、费用、收录状态多选筛选。
3. 机制标签：按资源与效果标签筛选，区分「产生」和「利用」。

本轮不做：数码兽、伙伴、道具页签的检索；拼音／首字母搜索（需引入拼音字典，体积与收益不匹配，中文输入法已能覆盖）；收藏或自定义标签；改动存档结构。

### 3.2 关键词搜索

| 规则 | 说明 |
| --- | --- |
| 搜索范围 | 卡名、基础效果、强化效果、所属形态名与搭档名、类型名、机制标签名、`N费` |
| 多词 | 空格分隔，所有词都要命中（AND）；如 `灼烧 护盾` 只返回同时涉及两者的牌 |
| 归一化 | 忽略空白与「·」；全角／半角数字、＋/+、×/x 视为相同；英文不分大小写。这样 `3灼烧` 能匹配「施加 3 灼烧」 |
| 同义词 | 词表映射到机制标签，如 群攻／全体／范围／AOE→群体；盾／格挡→护盾；烧／燃烧→灼烧；吸血／回血／治疗→回复；扣血／自伤→自损；过牌→抽牌；能量／费用回复→行动力 |
| 即时响应 | 边输入边过滤；用 `useDeferredValue` 避免手机输入卡顿，不做防抖延迟 |
| 命中提示 | 卡片下方显示命中位置：名称／效果／强化后／形态／机制。紧凑卡面不显示强化文本，因此只在强化后命中时必须给出提示，避免玩家以为搜索出错 |
| 清空 | 输入框右侧 ✕ 清空，不影响其他筛选。搜索框内按 Escape 时，有内容先清空，已为空才交给弹窗关闭。现有 `Modal` 在 document 上监听 Escape 并直接关闭，实施时需在搜索框内拦截该事件 |

搜索词与筛选条件之间是 AND 关系。

### 3.3 分类筛选

| 维度 | 选项 | 来源字段 | 选择方式 |
| --- | --- | --- | --- |
| 搭档 | 全部／基尔兽／妖狐兽／大耳兽／小妖兽／通用 | `unlockForm(s)` → `EVOLUTIONS[form].partner`；无 `unlockForm` 为通用 | 单选快捷条 |
| 来源形态 | 选定搭档后列出该搭档拥有专属牌的形态，按进化树顺序 | `unlockForm`／`unlockForms` | 多选 |
| 成长阶段 | 通用／成长期／成熟期／完全体／究极体 | `EVOLUTIONS[form].stage` | 多选 |
| 类型 | 攻击／技能／强化 | `kind` | 多选 |
| 费用 | 0／1／2 | 当前显示版本（基础或强化）的 `cost` | 多选 |
| 机制标签 | 见 3.4 | 由卡牌配置推导 | 多选 |
| 收录 | 全部／已收录／未收录 | 现有 `lit()` 口径 | 单选 |

组合规则：同一维度内为「或」，不同维度之间为「且」；机制标签例外，多个标签之间为「且」，因为玩家选「灼烧·施加」和「护盾·获得」时通常是想找同时具备两者的牌（当前结果为余烬护甲）。

共享技能（目前只有烈焰引爆，同属古拉兽与黑古拉兽）在任一所属形态下都能筛到。斗牛士兽 · 觉醒按究极体统计。未收录卡不参与形态筛选（见第4节），因此尚未到达的形态计数为0。

### 3.4 机制标签

标签由 `CardDef` 的最终配置推导，不解析文字，以保证与结算一致。按当前显示版本计算：基础版不读取 `upgradeDraw` 等辅助字段，强化版读取 `cardDefinition({ upgraded: true })` 的结果。目前强化后标签会发生变化的只有3张（能量装填、狐变虚、恶梦冲击波，强化后多出「抽牌」）。

| 分组 | 标签 | 推导规则（任一满足） | 基础版张数 |
| --- | --- | --- | --- |
| 灼烧 | 施加 | `burn` | 8 |
|  | 利用 | `special` 为 detonate／pyre，或 `burningBonus`、`burnShield` | 4 |
| 符印 | 施加 | `mark`、`burstMarkBonus` | 8 |
|  | 消耗 | `special` 为 markburst | 4 |
| 蓄能 | 获得 | `charge` | 4 |
|  | 利用 | `special` 为 cannon，或 `chargeSeg`、`chargedDamage` | 7 |
| 噬能 | 获得 | `devour`、`convert`、`killDevour`，或 `special` 为 devouraura | 10 |
|  | 消耗 | `special` 为 devour，或任一 `devourXxx` 消耗字段 | 13 |
| 护盾 | 获得 | `shield`、`burnShield` | 23 |
|  | 利用 | `special` 为 shieldhit，或 `shieldSpend` | 3 |
| 生命 | 自损 | `special` 为 sacrifice | 9 |
|  | 回复 | `heal`、`drain`、`drainRatio`、`devourHeal`、`refundSelfCostOnKill` | 10 |
| 效果 | 伤害 | `damage` | 63 |
|  | 群体 | `all` | 19 |
|  | 多段 | `hits > 1`、`devourHits`，或 `special` 为 windup | 15 |
|  | 抽牌 | `draw`、`killDraw` | 19 |
|  | 行动力 | `energy`，或 `special` 为 spinstep | 4 |
|  | 虚弱 | `weak`、`devourWeak` | 11 |
|  | 易伤 | `devourVuln` | 1 |
|  | 力量 | `strength`、`devourStrength` | 3 |
|  | 耗竭 | `exhaust` | 19 |
|  | 复制 | `special` 为 copy | 1 |
|  | 清故障 | `special` 为 purge | 1 |
|  | 条件触发 | `executeBonus`、`selfCostBonus`、`multiAttackDouble`、`burningBonus`、`chargedDamage`、`killDraw`、`killDevour`、`refundSelfCostOnKill`、`burstMarkBonus`，或 `special` 为 lure／izuna／spinstep／windup | 12 |

用原型脚本核对：107张牌每张至少有1个标签。几个典型查询的结果：「灼烧·利用」→ 烈焰引爆、双刃斩、圣炎之盾、末日审判；「符印·消耗＋群体」→ 封灭阵；「噬能·消耗＋回复」→ 噬能饱食、血腥宴席、腐毒之拥。

「产生／利用」成对出现，有两个用途：一是在筛选面板中并排展示；二是在详情页（3.7）推荐搭配牌。

维护约束：新增卡牌字段时，必须在标签映射中归类，或明确列入「不产生标签」清单，由测试强制检查（见第7节）。

### 3.5 强化版切换

工具栏增加「强化版」开关。打开后：卡面按强化版渲染（`upgraded: true`）；费用、机制标签、关键词匹配都按强化版计算；分面计数随之刷新。默认关闭。开关状态与筛选条件一起保留。

### 3.6 排序

| 排序 | 规则 |
| --- | --- |
| 费用（默认） | 费用升序 → 名称 |
| 成长阶段 | 通用 → 成长期 → … → 究极体 → 费用 → 名称（沿用现有逻辑） |
| 来源 | 通用 → 基尔兽 → 妖狐兽 → 大耳兽 → 小妖兽，搭档内按进化树形态顺序 → 费用 |
| 名称 | 中文排序（`localeCompare(..., 'zh')`） |
| 相关度 | 只在有关键词时出现并自动选中：名称命中 > 形态命中 > 机制命中 > 效果命中 > 强化后命中，同级再按费用。清空关键词后恢复之前的排序 |

### 3.7 结果区

结果区包含以下内容：
- 计数行：「共 N 张 · 其中 M 张未收录」。
- 已选条件条：每个条件一枚小标签，点击 ✕ 移除；末尾为「清除全部」。
- 空结果：显示「没有符合条件的卡」，并给出放宽建议。具体做法是逐个去掉已选条件试算，按结果数从多到少给出最多2条建议，例如「去掉『2 费』可看到 5 张」，点击即移除该条件。

### 3.8 卡片详情（第二期）

点击结果中的卡片，打开详情底部面板：

| 区块 | 内容 |
| --- | --- |
| 卡面 | 大尺寸卡牌 |
| 强化对比 | 复用 `CardEffectPreview` 的「强化前／强化后」对比，含费用变化 |
| 来源 | 所属搭档、形态、阶段；共享技能列出全部所属形态 |
| 获取方式 | 复用 `skillDescription()` 文案；攻击指令说明不进入奖励与商店 |
| 机制标签 | 点击即作为筛选条件应用，并回到结果列表 |
| 搭配参考 | 按「产生↔利用」配对，列出同搭档内的对应牌，最多6张。例如热浪（灼烧·施加）→ 烈焰引爆、双刃斩、圣炎之盾、末日审判 |
| 进化路线 | 「在进化路线中查看」按钮，打开进化树并定位到所属形态；需给 `EvolutionTree` 增加 `initialForm` 参数 |

详情面板支持左右滑动或方向键，在当前结果中切换上一张／下一张。

### 3.9 本局联动（第二期）

有进行中的冒险时，筛选面板顶部增加「本局」分组：
- 卡组中：当前永久卡组持有的牌；结果卡片下方显示「卡组 ×N」，详情页显示持有数与强化数。
- 本局可获取：`cardPool(run)` 中的牌，即当前会出现在奖励与商店的牌。

`Codex` 接收 `run`，但结果中的 `GameCard` 不传入 `run`：卡面在战斗中会按 `playCost(run, …)` 显示减费（如觉醒斗牛士兽第二张攻击0费），图鉴应展示配置费用。没有进行中的冒险时，这一分组不显示，保留下来的本局条件也不生效。

## 4. 防剧透口径

沿用现状，不改变收录规则。注意：原提案此处误写为「未收录卡照常显示所属形态名」；实际现状是未收录卡隐藏卡面的形态标签（`.codex-card-slot.locked .card-origin`），实施按实际现状处理：
- 未收录的卡片照常参与卡名、效果、机制、阶段、类型、费用与搭档检索，结果中置灰并标「未收录」，卡面效果照常可读。
- 未收录卡不按形态名命中关键词，也不参与「来源形态」筛选，避免通过检索反推所属形态。
- 「收录」筛选与计数沿用原 `lit()` 口径，现移至 `isCardCollected()`：基础形态与通用卡常亮；进化形态卡到达过（`meta.discovered`）即点亮；小妖兽在别西卜兽扫描未满100%前置灰。共享技能到达任一所属形态即点亮（原实现只看第一个形态）。
- 详情页对未收录卡只显示搭档与阶段，并提示「到达对应形态后收录」；不展示形态名、进化条件，也不提供进化树跳转。
- 数码兽页签的剪影规则不变。

## 5. 数据与实现

### 5.1 新增纯逻辑模块 `src/game/cardIndex.ts`

```ts
export type CardTag =
  | 'burnApply' | 'burnUse' | 'markApply' | 'markSpend'
  | 'chargeGain' | 'chargeUse' | 'devourGain' | 'devourSpend'
  | 'shieldGain' | 'shieldUse' | 'selfCost' | 'heal'
  | 'damage' | 'aoe' | 'multiHit' | 'draw' | 'energy' | 'weak'
  | 'vulnerable' | 'strength' | 'exhaust' | 'copy' | 'purge' | 'conditional';

export const TAG_INFO: Record<CardTag, {
  label: string;            // 「灼烧·施加」
  group: 'burn' | 'mark' | 'charge' | 'devour' | 'shield' | 'life' | 'effect';
  aliases: string[];        // 同义词
  pair?: CardTag;           // 产生↔利用配对
}>;

export function cardTags(def: CardDef): CardTag[];

export interface CardIndexEntry {
  id: string;
  partner: Partner | 'common';
  forms: string[];          // unlockForm(s)，通用为空
  stage: -1 | 0 | 1 | 2 | 3;
  base: { def: CardDef; tags: CardTag[]; doc: string };   // doc 为归一化后的检索文本
  upgraded: { def: CardDef; tags: CardTag[]; doc: string };
}
export function buildCardIndex(): CardIndexEntry[];       // 模块级缓存，只算一次

export interface CardQuery {
  text: string;
  partner: Partner | 'common' | 'all';
  forms: string[]; stages: number[]; kinds: CardKind[]; costs: number[];
  tags: CardTag[]; collection: 'all' | 'lit' | 'locked';
  upgradedView: boolean; sort: 'cost' | 'stage' | 'source' | 'name' | 'relevance';
}
export function searchCards(index: CardIndexEntry[], q: CardQuery, lit: (d: CardDef) => boolean): {
  results: { entry: CardIndexEntry; matchedIn: MatchField[] }[];
  facets: Record<string, Record<string, number>>;   // 分面计数
  relaxHints: { remove: string; count: number }[];  // 空结果建议
};
```

模块不依赖 React，可在 vitest 中直接测试，也可供审核脚本（`tools/audit_card_balance.mjs`）复用标签。107张卡全量过滤开销可以忽略，不需要额外索引结构。

### 5.3 状态保留

## 9. 实施记录（2026-10-12）

与提案的差异：
- 第5.1节的接口是提案草图，实际签名以 `src/game/cardIndex.ts` 为准（如 `searchCards(query, ctx)` 内部使用缓存索引，并返回 `filters`）。
